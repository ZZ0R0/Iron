# [20700] Closures / lambdas + `map`/`filter`

- Version : V6 · Milestone : M5+ · Statut : draft · Dépend de : 20100, 40100 · Invariants : I6, I1, I10

## Objectif
Fonctions anonymes (closures) capturant leur environnement → closures Rust. Débloque `map`/`filter`/`fold`.

## Périmètre
- Syntaxe lambda : `fn(x): x + 1` ou `\x -> x + 1` (à trancher au cadrage).
- Capture par valeur (clone/move, I1) ; projection vers `Fn`/`FnMut` Rust (I6).
- Built-ins `map(lst, f)`, `filter(lst, f)` → `.iter().map(..).collect()` / `.filter(..)`.

## Hors-périmètre
Capture par référence longue durée (lifetimes nommés) ; `move` closures explicites.

## Comportement attendu (Iron → Rust)
- `inc = fn(x): x + 1` → `let inc = |x| x + 1;`.
- `map([1,2,3], fn(x): x * 2)` → `vec![1,2,3].iter().map(|x| x * 2).collect::<Vec<_>>()`.

## Contrat / interface
AST `ExprKind::Lambda { params, body }` ; `Type::Fn(params, ret)`. Lowering → closure Rust ; capture
réglée par la sémantique valeur (I1). Inférence des types de params de lambda **laissée à rustc** (I2/I6).

## Source maps
Le corps de lambda porte ses `Span` (I8).

## Critères d'acceptation
Une lambda stockée + appelée ; `map`/`filter` sur une `list[T]` → compile + exécute ; capture correcte.

## Décomposition
→ planif. Structurant (nouveau type fonction).

## Risques / questions ouvertes
- 🔶 Syntaxe (`fn(x):` vs `\x ->`) — décision de cadrage.
- 🔶 Type des closures (`impl Fn` en retour, boxing `Box<dyn Fn>` si stocké) — projection à figer.
