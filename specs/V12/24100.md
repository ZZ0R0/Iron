# [24100] Suivi des paramètres de type génériques + monomorphisation des scalaires

- Version : V12
- Milestone : M12
- Statut : draft
- Dépend de : [20100] inférence locale, [50900] types externes à API
- Invariants applicables : I2 (jamais d'`unsafe`), I6 (sous-ensemble Iron), I10 (codegen `TokenStream`)

## Objectif

Permettre à Iron d'utiliser les **types externes génériques sur un type** (`Point<T>`, `Vector3<T>`,
`Array<T>`…) dont l'API prend/rend le paramètre `T` — aujourd'hui un mur dur. Révélé par `geo` : `Point<T:
CoordNum>` expose `new(x: T, y: T) -> Self` et `distance() -> T` ; comme Iron ne suit pas `T`, **rien** ne se
binde utilement (ni construction ni résultat scalaire).

## Périmètre

- **Suivi du paramètre de type** d'un type externe : distinguer `Point<f64>` de `Point<i32>` au lieu d'un
  unique `Extern("Point")`. L'inférence propage `T` depuis le site de construction (`Point.new(1.0, 2.0)` ⇒
  `T = f64`) jusqu'aux retours (`distance() -> f64`).
- **Monomorphisation des bornes scalaires** vers un type concret par défaut quand le site d'appel le fixe
  (Rust infère `T` des arguments concrets ; Iron émet `Point::new(1.0, 2.0)` et laisse Rust trancher `T`).

## Hors-périmètre

- Reconnaître des **noms de traits de crate** (`CoordNum`, `Scalar`…) comme « numériques » → **interdit**
  (cas-par-cas). La résolution doit venir du **site d'appel** (types des arguments), pas d'une table de noms.
- Génériques d'ordre supérieur, const-génériques, GAT.

## Comportement attendu

```
# Iron
p = Point.new(0.0, 0.0)       # T inféré = f64 (depuis les args)
q = Point.new(3.0, 4.0)
d = p.euclidean_distance(q)    # -> f64 (T propagé)
print(d)                       # 5.0

# Rust généré (T laissé à l'inférence Rust)
let p = geo_types::Point::new(0f64, 0f64);
let q = geo_types::Point::new(3f64, 4f64);
let d = geo::EuclideanDistance::euclidean_distance(&p, &q);   // f64
println!("{}", d);
```

Idée directrice : **ne pas monomorphiser dans le binder** (qui n'a pas le site d'appel) — binder `T` comme
un **paramètre**, et laisser l'inférence Iron + l'inférence Rust le résoudre au site d'appel.

## Contrat / interface

- `ExternType` porte ses paramètres de type ; `Type::App("Point", [T])` (déjà présent dans l'IR) devient le
  type d'une instance, `T` unifié par l'inférence.
- `map_type` : un générique en **position d'argument** se lie en passe-système (l'arg concret fixe `T`) ; en
  **position de retour seule**, `T` reste lié au receveur (`self : Point<f64>` ⇒ `-> f64`).

## Source maps

N/A au niveau type ; le lowering préserve les spans existants (les appels restent 1:1).

## Critères d'acceptation

- `geo` : `Point.new(0.0,0.0).euclidean_distance(Point.new(3.0,4.0))` compile et imprime `5`.
- Un type générique mono-instancié à deux scalaires différents dans le même programme ne se confond pas.
- gate-v11 reste VERT (aucune régression sur les types non génériques).

## Risques / questions ouvertes

- ❓ Jusqu'où propager `T` sans inférence Rust complète côté Iron ? (laisser Rust trancher autant que possible.)
- ❓ Que faire d'un `T` **non résolu** au site d'appel (générique en retour seul, sans receveur typé) → sauter ?
- 🔶 Interaction avec la sémantique par valeur : `Point<T>` doit rester `Copy`/clonable selon `T`.
