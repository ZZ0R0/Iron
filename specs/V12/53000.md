# [53000] Runtime async (`tokio` / `async fn` / `.await` exécutés)

- Version : V12
- Milestone : M12
- Statut : draft (cadrage)
- Dépend de : [40200] appels externes, [50900] types externes
- Invariants applicables : I2, I9 (pipeline), I10, I13 (erreurs unifiées)

## Objectif

Exécuter du code **asynchrone** : serveurs web (axum), bots (teloxide), clients réseau/IoT (redis,
tungstenite, hickory, rumqttc, reqwest). Iron a `await` **en surface** (lowering présent) mais **aucun
exécuteur** : pas de `tokio`, pas de `Future` piloté, pas de `async fn main`. Sans runtime, tout ce qui rend
un `Future` est inappelable.

## Périmètre

- Un **exécuteur** (tokio) câblé : `def main()` async → `#[tokio::main]` ; les fns externes `async` →
  `.await` (déjà émis) **réellement pilotées**.
- Les types `Future`/`async` des crates exposés proprement (un appel `async` rend une valeur **awaitable**).

## Hors-périmètre

- Concurrence structurée avancée (`select!`, `join!` arbitraires) en V12 — viser le **séquentiel async**
  (`await` l'un après l'autre) d'abord.
- Async **sans `std`** (embarqué async) → hors [43000] et [53000] pour l'instant.

## Comportement attendu (esquisse)

```
# Iron (forme cible)
async def main():
    resp = await get("https://api.example.com/data")   # ureq/reqwest async
    print(resp.status())
```

## Questions ouvertes (cadrage)

- ❓ Déclarer `main` async implicitement si une fn async est appelée, ou explicitement (`async def`) ?
- ❓ `tokio` comme dépendance **bénie** (toujours ajoutée) vs détectée depuis les bindings async ?
- 🔶 Interaction avec [35000] (boucles de jeu async) et [52800] (io async).

## Critères d'acceptation (cible)

- Un client HTTP async (`get(url).await`) compile, tourne, imprime un statut.
- gate-v11 VERT.

> **Note.** Iron a déjà `ExprKind::Await` ; le manque est le **runtime + le câblage `#[tokio::main]`**. Gros
> chantier ciblé (web/bots/IoT), distinct du modèle event-loop synchrone [35000].
