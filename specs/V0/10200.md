# [10200] Parser + AST

- Version : V0
- Milestone : M0
- Statut : draft
- Dépend de : 10100
- Invariants applicables : I9

## Objectif
`Vec<Token>` → `Ast` (README §4.2), avec attribution des `NodeId` (pré-ordre DFS, dense dès 0, §3) et **convergence des deux syntaxes de bloc vers le même AST**.

## Périmètre
Grammaire du sous-ensemble V0 (§1) : items `fn`/`struct`, instructions, expressions, blocs `:`-indentés **ou** `{}`. Désambiguïsation : `{…}` **bloc** vs `{k:v}` **dict** par **position** (instruction vs expression) ; `S(champ=expr)` (args nommés) → `StructLit`, `f(args)` (positionnels) → `Call`.

## Hors-périmètre
Typage (→ 20100/20200) ; résolution sémantique nom struct↔fn au-delà de la distinction syntaxique nommé/positionnel.

## Comportement attendu (observable)
- Produit un `Ast` où un `body` est une **liste de `Stmt` identique quelle que soit la syntaxe source** ; seul le `Span` reflète l'origine.
- Attribue `NodeId` en **pré-ordre DFS**, dense dès 0 (clé partagée §3).
- `Span` d'un nœud = du 1ᵉʳ au dernier token le composant.
- Erreurs de syntaxe au `Span` fautif.

## Contrat / interface
Produit `Ast` (README §4.2). Consomme `Vec<Token>` (10100).

## Source maps
Chaque nœud porte son `Span` — base de tout le mapping I8 en aval.

## Critères d'acceptation
- Programme V0 (§6) : **les deux écritures (`:` et `{}`) → AST identique** (hors spans).
- `NodeId` denses, pré-ordre, sans trou.
- `{1: 2}` en position expression → `DictLit` ; `{ stmt }` en position bloc → bloc.
- `S(x=1)` → `StructLit` ; `f(1)` → `Call`.

## Décomposition
→ phase 2 (`planification/`).

## Risques / questions ouvertes
- ❓ imbrication inter-styles (`{}` contenant un bloc `:` ⇒ réactivation off-side) — règle exacte à figer avec 10100.
- ❓ args mixtes nommés/positionnels : **interdits** en V0 (sinon ambiguïté struct/call) — à confirmer.
