# [20100] Inférence locale (monotypes, structs, collections)

- Version : V0
- Milestone : M1
- Statut : draft
- Dépend de : 10200
- Invariants applicables : I6

## Objectif
Annoter chaque `Expr` d'un monotype (`TypeMap`, README §4.4) : littéraux, variables, opérateurs, structs, **éléments de collections**, appels.

## Périmètre
Inférence ascendante + **vérification** des annotations explicites. Types : primitifs, structs, `List`/`Dict` natifs (§4.3). Les signatures de `fn` servent l'inférence des appels.

## Hors-périmètre
`Option`/`Result` par flux (→ 20200) ; ownership (→ 30100) ; génériques utilisateur (→ V3).

## Comportement attendu (observable)
- `int`→`I64`, `float`→`F64`, `bool`→`Bool`, `str`→`Str` ; `[…]`→`List(T)`, `{k:v}`→`Dict(K,V)` (T,K,V des éléments) ; `e[i]`→élément ; `e.f`→type du champ ; `S(...)`→`Struct(S)` ; appel→retour de la `fn`.
- Annotation explicite (`x: T`, params, retour) **vérifiée** ; incohérence = erreur typée au `Span` (I2 : remontée propre, jamais d'`unsafe`).
- Projection I6 : tout `Type` inféré se mappe vers Rust.

## Contrat / interface
Produit `TypeMap : NodeId→Type`. Consomme `Ast` (10200).

## Source maps
N/A (annotation). Les erreurs de type pointent un `Span`.

## Critères d'acceptation
- Tout `Expr` du programme V0 a un `Type` ; annotations vérifiées ; mismatch → erreur au bon `Span`.
- `list`/`dict` d'éléments homogènes inférés correctement.

## Décomposition
→ phase 2 (`planification/`).

## Risques / questions ouvertes
- ❓ collection **vide** (`[]`, `{}`) : élément indéterminé → exiger une annotation en V0 (défaut) ?
- ❓ numériques : `i64`/`f64` par défaut, pas d'inférence de largeur — à figer.
