# [10400] Tuples : type, littéral, destructuring, retour multiple

- Version : V7 · Milestone : M1 · Statut : draft · Dépend de : 10200, 20100, 20300 · Invariants : I1, I6, I9

## Objectif
Donner à Iron les **tuples** (produits anonymes) pour le **retour multiple** et l'**affectation
déstructurée** — ergonomie absente aujourd'hui (un seul retour, une seule cible d'affectation).

## Périmètre
- Type `(A, B, …)`, littéral `(a, b)`, déstructuring `a, b = expr` / `a, b = f()`, retour multiple
  `return a, b`, tuple en paramètre/champ, **motif tuple** en `match`, indexation `t.0`/`t.1`.

## Hors-périmètre
- Tuples nommés (→ struct, existant) ; spread `*t` (V8) ; tuple-structs.

## Comportement attendu
- `a, b = 1, 2` → `let (mut a, mut b) = (1i64, 2i64);`.
- `fn divmod(x, y) -> (i64, i64): return x // y, x % y` → `fn divmod(...) -> (i64, i64) { return (x / y, x % y); }`.
- `match p: (0, y): …` → `(0, y) => …`.

## Contrat / interface
IR (fondation D0, gelé vague 1) : `Type::Tuple(Vec<Type>)`, `ExprKind::Tuple(Vec<Expr>)`,
`Pattern::Tuple(Vec<Pattern>)` ; `StmtKind::Let`/`Assign` acceptent une **cible tuple**. `infer` :
type produit + liaison des cibles. `lower` : tuples Rust ; déstructuring → `let (a, b) = …`.

## Source maps
Marqueur instruction sur `Let`/`return` — inchangé (I8).

## Critères d'acceptation
- `a, b = divmod(17, 5)` ; `print(a)`/`print(b)` → 3 / 2.
- Retour multiple + motif tuple `(0, y)` compilent + s'exécutent ; corpus inchangé.

## Décomposition
→ planif : fondation IR (vague 1) ; puis tâches parser (littéral/cible), infer (produit), lower (déstructuring).

## Risques / questions ouvertes
- ✅ `(a)` = parenthèses ; tuple-1 = `(a,)` (convention Rust/Python).
- 🔶 Collision littéral tuple `(…)` vs expression parenthésée — désambiguïsée par la virgule.
