# [60400] Erreurs de type niveau Iron (avant `rustc`)

- Version : V7 · Milestone : M6 · Statut : draft · Dépend de : 20100, 60100 · Invariants : I2, I8

## Objectif
Détecter les erreurs de type **fréquentes** au niveau Iron et émettre un message clair **avant** `rustc` —
aujourd'hui tout passe par la remontée `rustc` (correcte mais parfois cryptique). Reste optimiste (I2 :
`rustc` demeure le filet, on ne duplique pas le borrow-checker).

## Périmètre
- Erreurs « faciles » : opérateur entre types incompatibles (`i64 + str`), appel d'arité fausse, champ/
  méthode inexistant, motif de variante inconnu, `return` de mauvais type évident.

## Hors-périmètre
- Vérification de type complète / borrow-check (→ `rustc`, I2) ; inférence globale.

## Comportement attendu
- `x = 1 ; y = x + "oops"` → `erreur Iron : '+' entre i64 et str (ligne:col)` **avant** le lowering.
- `f(1, 2)` où `f` prend 1 param → `erreur : f attend 1 argument, 2 fournis`.
- Cas non couverts → silencieux côté Iron, `rustc` tranche (I2).

## Contrat / interface
Passe `typecheck.rs` (best-effort) sur AST + `TypeMap` → `Vec<CompileError>` au `Span` Iron. Lancée après
`infer`, avant `lower` ; si erreurs → stop avec message Iron (pas de Rust généré).

## Source maps
Message porte le `Span` Iron directement (pas de remontée `rustc` nécessaire pour ces cas) — I8.

## Critères d'acceptation
- `i64 + str`, arité fausse, champ inexistant → messages Iron clairs aux bons `Span`, sans atteindre `rustc`.
- Aucun faux positif sur le corpus (37/37 toujours compilés) ; cas non couverts → toujours délégués à `rustc`.

## Décomposition
→ planif : framework typecheck, erreurs opérateur/arité, champ/méthode/variante.

## Risques / questions ouvertes
- 🔶 Risque de **faux positifs** vs inférence best-effort → ne signaler que les cas **certains** (sinon laisser `rustc`).
