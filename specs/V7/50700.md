# [50700] Fns Rust génériques + impl de traits standards

- Version : V7 · Milestone : M5 · Statut : draft · Dépend de : 50500, 20300 · Invariants : I6, I7

## Objectif
Deux interops manquantes : appeler des **fns Rust génériques** bindées, et **implémenter des traits std**
(`Display`, `Iterator`, `From`) sur des types Iron — pour une intégration idiomatique.

## Périmètre
- Binding/appel d'une fn générique mono-instanciée (`fn f<T>(x: T)` usée à type concret).
- `impl Display for Point: …` / `impl Iterator …` côté Iron → `impl` Rust correspondant.

## Hors-périmètre
- Génériques de binding pleinement paramétriques (V8) ; traits à types associés complexes.

## Comportement attendu
- `impl Display for Point: fn fmt(self) -> str: return f"({self.x}, {self.y})"` → `impl std::fmt::Display
  for Point { fn fmt(&self, f: …) -> … { write!(f, "({}, {})", self.x, self.y) } }`.
- Une fn bindée `max_by<T: Ord>(…)` appelée sur `list[i64]` → instanciation `T = i64`.

## Contrat / interface
Parser/IR : `impl <Trait std> for <Type>` reconnu ; map des méthodes-trait vers la signature Rust attendue
(`Display::fmt`, `Iterator::next`). `lower` : `impl` Rust idiomatique. `bind` : fns génériques mono-usage.

## Source maps
Erreur d'impl de trait → remontée `rustc` au `Span` Iron (I8).

## Critères d'acceptation
- `impl Display for Point` → `print(p)` affiche `(3, 4)` via `{}`.
- Une fn bindée générique appelée à type concret compile + s'exécute.

## Décomposition
→ planif : `impl Trait-std` (parser/lower), mapping méthodes-trait, fns génériques bindées.

## Risques / questions ouvertes
- 🔶 Signature `fmt` : Iron `-> str` vs Rust `(&self, &mut Formatter) -> fmt::Result` — adapter au lowering.
- 🔶 `Iterator` exige `type Item` — borné à un cas simple en V7, le reste V8.
