# [50600] Capacités du moteur++ — règles générales de dérivation (réalisation V15)

- Version : V14 (cadrage) → réalisation **V15**
- Milestone : binding-système
- Statut : draft
- Dépend de : [50400] (deux couches), [50500] (portée connue & rapport), [24500] (const-gen V13), [52800] (io)
- Invariants applicables : I6, I7, I7bis, I15

## Objectif
Énumérer et **contractualiser** les **règles générales** (zéro nom de crate) qui font passer des **familles
entières** d'items de `skipped` à `bound`, pour viser **60/80**. Chaque capacité = **une règle de projection
générale** + la **classe de `SkipReason`** ([50500]) qu'elle résorbe + les familles de crates débloquées + un
**critère testable**. **La réalisation est V15** ; V14 fige le **contrat** de chaque règle pour que le fan-out
V15 soit parallélisable (pistes à ownership disjoint, classes de skip distinctes).

> **Garde-fou.** Chaque règle se justifie par une **généralité lisible dans rustdoc** (un alias, un `impl
> Trait for T`, un `Const<N>`, un pattern builder), **jamais** par la connaissance d'un crate. Si une règle
> ne tient que pour un crate nommé, elle n'entre pas ici — elle devient de la **curation manuelle** ([50400]).

## Périmètre
Les 4 capacités C1–C4, leur règle, leur classe de skip cible, leur critère d'acceptation.

## Hors-périmètre
- L'implémentation détaillée (lowering, `bind.rs`) → planif V15.
- La curation manuelle des items qu'aucune règle ne couvre → [50400].

## Comportement attendu

### C1 — Alias monomorphisé → type nominal  *(résorbe `ConstGenericShape` ctors-par-dimension ; haut levier)*
Un `impl` inhérent porté par une **monomorphisation concrète** d'un type générique
(`impl<T> Matrix<T, Const<3>, Const<1>, …> { fn new(x,y,z) }`) pour laquelle rustdoc expose un **alias**
(`type Vector3<T> = Matrix<T, Const<3>, Const<1>, …>`) devient une **méthode/ctor sur le type nominal de
l'alias** — pas sur la base générique (où il collisionnerait avec les autres dimensions).
```
# auto-dérivé, SANS nommer nalgebra (la règle lit l'alias + l'impl monomorphisé depuis rustdoc) :
extern type Vector3 { ctor new(x: f64, y: f64, z: f64) -> Vector3 = "nalgebra::Vector3::<f64>::new" }
```
- **Iron → Rust** : `Vector3.new(1.0, 2.0, 3.0)` → `nalgebra::Vector3::<f64>::new(1.0, 2.0, 3.0)`.
- **Débloque** : nalgebra, ndarray, rustfft, rapier2d, smartcore (familles **dimensions**, ~6-8 crates).
- **Pourquoi c'était un « mur »** : on **expansait** l'alias vers la base ([24500] B33) → collision `Matrix.new`.
  C1 fait l'**inverse** : garder l'alias **nominal** et y rattacher l'impl monomorphisé qui le vise.

### C2 — Méthodes de trait projetées  *(résorbe `GenericTraitMethod`)*
Une **méthode de trait** portée par un type concret via `impl Trait for Type` devient une **méthode du type
implémenteur**, ses paramètres génériques matérialisés par les sentinelles existantes (`@arr`, `@read`,
`@write` — [24500]/[52800]). La règle générale = **« projeter les méthodes d'un impl-trait sur le type qui
l'implémente »**, **pas** « connaître le trait `Aead` ».
```
# impl Aead for Aes256Gcm  →  méthodes projetées sur Aes256Gcm (sans nommer aead) :
extern type Aes256Gcm {
    method encrypt(nonce: list[u8], pt: list[u8]) -> Result[list[u8]] = "aead::Aead::encrypt"
}
```
- **Iron → Rust** : `cipher.encrypt(nonce, pt)` → `aead::Aead::encrypt(&cipher, nonce.into(), pt.as_ref())`.
- **Débloque** : aes-gcm, chacha20 (AEAD), et tout crate exposant ses opérations via un trait standardisé.
- **Risque** : matérialiser des **génériques de méthode de trait** ; s'appuie sur les sentinelles octets/io
  existantes. La plus délicate avec C4.

### C3 — Const-génériques portés dans le modèle de types  *(complète C1 ; résorbe `ConstGenericShape` résiduel)*
Étendre `Type::ExternApp` (V12) aux **arguments const** (`Const<N>` / littéraux) pour exprimer les shapes
**quand C1 ne suffit pas** (fn libres `f<const N: usize>()`, types paramétrés par une valeur sans alias dédié).
- **Iron → Rust** : un type `Foo[N]` porté par const → `Foo::<N>`.
- **Débloque** : usages const-génériques **au-delà** des alias-dimension (C1 couvre les ctors usuels ; C3 le reste).

### C4 — Modèle builder/flux  *(résorbe `StreamBuilderApi`)*
Reconnaître le pattern **builder consommant/rendant `self`** (`Encoder::new(w) → .write_all(..) → .finish()`)
et l'exposer comme **chaînage de méthodes** Iron, au lieu d'exiger une fn one-shot à puits.
- **Iron → Rust** : `Encoder.new(sink).write_all(data).finish()` → la chaîne Rust équivalente.
- **Débloque** : flate2 (compression streaming) et les API de flux / sérialiseurs incrémentaux.
- **Risque** : le plus structurel (état porté entre appels) ; peut rester **partiel** — auquel cas 50500 le
  **classe** honnêtement plutôt que de prétendre l'avoir couvert.

## Contrat / interface
- Chaque capacité **n'ajoute aucun nom de crate** dans `ironc/src/*.rs` (garde-fou ci-dessus).
- Chaque capacité **fait baisser** un compteur de `SkipReason` précis dans le rapport [50500] — c'est sa
  **mesure de succès objective**, pas une impression.
- Les capacités sont **indépendantes** (classes de skip disjointes) → **pistes parallèles** en V15.

## Source maps
Chaque règle émet du Rust via TokenStream (I10) avec préservation des spans (I8) comme tout lowering ; la
**réduction de la classe de skip** correspondante dans le rapport [50500] est la trace de complétude.

## Critères d'acceptation
- **C1** : `Vector3.new(1.0,2.0,3.0).norm()` (nalgebra, run réel) ; classe `ConstGenericShape` **disparaît**
  du rapport pour les ctors-dimension de nalgebra/ndarray.
- **C2** : aes-gcm chiffre **et** déchiffre un message (run réel) ; classe `GenericTraitMethod` disparaît
  pour les méthodes AEAD.
- **C3** : un usage const-générique hors-alias compile (run réel).
- **C4** : flate2 compresse → octets puis décompresse → message d'origine (run réel) ; `StreamBuilderApi`
  disparaît pour le pattern Encoder/Decoder.
- **Global** : la **couverture calculée** ([50500]) **monte** mesurablement après chaque capacité ; cible
  agrégée **60/80** (HW remplacés non-trivialement, cf. README §politique).

## Décomposition
→ **V15, fan-out** après la vague-1 fondation ([50400]/[50500]) :
- `planify-2.1` ≈ C1 (alias→nominal), `planify-2.2` ≈ C2 (trait-méthodes), `planify-2.3` ≈ C3 (const-gen),
  `planify-2.4` ≈ C4 (builder/flux) — pistes parallèles, ownership disjoint, **chacune mesurée par sa classe
  de skip**. (Noms/numéros figés à la planif V15.)

## Risques / questions ouvertes
- **🔶 60/80 non garanti.** Il dépend de C1 (tractable, haut levier) + C2 (délicate) + le remplacement
  non-trivial des HW. 50500 le rend **mesurable** ; je ne le **promets** pas, je le **contractualise**.
- **❓ C4 builder** : l'état porté entre appels peut dépasser la projection simple → possiblement **partiel**,
  classé honnêtement par 50500.
- **🔶 C2 vs sentinelles** : la matérialisation des génériques de méthode de trait réutilise `@arr`/`@read`/
  `@write` ; un cas hors-sentinelle existante = nouveau skip classé, pas un drop.
