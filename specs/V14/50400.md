# [50400] Système de binding — moteur auto + curation manuelle (deux couches qui composent)

- Version : V14
- Milestone : binding-système
- Statut : draft
- Dépend de : [50200] (`.iri` manuels), [50300] (auto-gen rustdoc), [52700] (façade re-export, merge last-wins)
- Invariants applicables : I7, I7bis, I6, I14

## Objectif
Définir le binding comme un **système à deux couches** plutôt qu'un générateur monolithique : une couche
**auto-générée** par le moteur (`ironc add`, niveau I7-3) et une couche **curée à la main** (niveau I7-2),
qui **composent** sans se détruire. Aujourd'hui les deux existent (`std.iri` est 100% curé ; `ironc add`
produit de l'auto) mais leur **coexistence n'est pas spécifiée** : régénérer écraserait une curation. V14
fige le modèle : **la curation gagne, la régénération ne l'efface jamais.** C'est la condition pour que
« écrire un binding à la main » soit un **filet sanctionné** (ton modèle Nim), pas un hack jetable.

## Périmètre
- Le **modèle de composition** des deux couches (emplacement, clé de merge, qui gagne).
- La **régénérabilité** de la couche auto sans perte de la couche curée.
- Le statut de `std.iri` comme cas-limite (curé pur, pas de couche auto — la std n'est pas un crate cargo).

## Hors-périmètre
- La **taxonomie des raisons de non-binding** et le **rapport** → [50500].
- Les **règles de dérivation** qui augmentent la couche auto (C1–C4) → [50600].
- L'**UX CLI** précise de `ironc add` (flags, chemins de sortie définitifs) → réalisation/`7xxxx`.

## Comportement attendu

**Deux fichiers, une clé de merge.**
- `ironc add <crate>` produit `<crate>.gen.iri` — couche **auto**, **machine-owned**, **régénérable à
  volonté**, **jamais éditée à la main** (un en-tête le déclare : `# AUTO-GÉNÉRÉ — ne pas éditer ; voir <crate>.iri`).
- `<crate>.iri` (sans `.gen`) — couche **curée**, **human-owned**, **optionnelle**. Absente → le système
  fonctionne en **pur-auto** (rétrocompatible).
- À l'import d'un crate, le système charge **d'abord** `<crate>.gen.iri`, **puis** `<crate>.iri`. La
  sémantique de merge est **last-wins par entrée** (déjà en place pour la façade re-export [52700]).

**Clé de merge = (kind, nom-Iron).** Une entrée curée écrase l'entrée auto de **même kind et même nom** :
- `extern fn foo` curé écrase `extern fn foo` auto.
- `extern type T { ... }` curé écrase le bloc `T` auto **en entier** (pas de fusion intra-type : si tu cures
  `T`, tu possèdes tout `T` — règle simple, prévisible).
- Une entrée curée **sans** homologue auto = **ajout** pur.

```
# nalgebra.gen.iri  (AUTO — régénéré par `ironc add nalgebra`)
extern type Vector3 { }          # le moteur n'a pas su le ctor → bloc vide (cf. rapport 50500)

# nalgebra.iri  (CURÉ — écrit à la main, GAGNE)
extern type Vector3 {
    ctor new(x: f64, y: f64, z: f64) -> Vector3 = "nalgebra::Vector3::<f64>::new"
}
```
→ à l'import, `Vector3` curé l'emporte. **`ironc add nalgebra` peut être relancé** (nouvelle version du
crate) : il réécrit `nalgebra.gen.iri`, **laisse `nalgebra.iri` intact**.

**`std.iri` = invariant du modèle.** La std n'est pas un crate cargo → **pas** de `std.gen.iri`. `std.iri`
est **100% curé** et démontre que la couche curée est un citoyen de première classe, pas un patch.

## Contrat / interface
- **Entrée** : un crate cargo résolu (`ironc add`) ; optionnellement un `<crate>.iri` curé pré-existant.
- **Sortie** : `<crate>.gen.iri` (toujours) + le `.iri` curé (préservé). À l'import, la **fusion** des deux
  est l'ensemble de bindings effectif, **curé gagnant par (kind, nom)**.
- **Format `.iri` inchangé** (I14) : aucune nouvelle syntaxe. La nouveauté est **purement** le modèle deux-couches
  + last-wins. Le parseur `.iri` last-wins existe déjà ([52700]) ; V14 le **généralise** à la paire gen/curé.
- **Décision figée** : la clé de merge est `(kind, nom-Iron)` ; le bloc-type est l'**unité atomique** d'override.

## Critères d'acceptation
- `ironc add <crate>` écrit `<crate>.gen.iri` avec l'en-tête « AUTO — ne pas éditer ».
- Un `<crate>.iri` curé présent **écrase** l'entrée auto homonyme à l'import (test : entrée auto opaque +
  entrée curée typée → la typée est utilisée, programme Iron compile).
- **Relancer `ironc add`** réécrit `<crate>.gen.iri` et **laisse `<crate>.iri` inchangé** (test : hash du
  `.iri` curé identique avant/après régénération).
- Sans `<crate>.iri`, le système marche en pur-auto (rétrocompat : corpus V12/V13 toujours vert).

## Risques / questions ouvertes
- **❓ Emplacement définitif** des `.gen.iri`/`.iri` (dossier `bindings/` du projet utilisateur vs cache).
  Aujourd'hui `ironc add` écrit dans `/tmp`. Décision UX → réalisation (`7xxxx`), pas bloquant pour le modèle.
- **❓ Granularité d'override intra-type** : on fige « curer un type = posséder tout le type » (simple). Si
  un jour on veut curer **une seule méthode** d'un type auto, ce sera une extension (notée, pas faite).
- **🔶 Versionnage** : un `.gen.iri` est lié à une version de crate (`read_lock_versions` existe). Un `.iri`
  curé qui survit à un bump majeur peut diverger → le **rapport** [50500] doit signaler une entrée curée
  qui ne correspond plus à aucun item auto (« curation orpheline »).
