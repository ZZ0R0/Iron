# [60900] Source-maps granularité expression

- Version : V9.1 · Milestone : M9.1 · Statut : draft · Dépend de : 60100, 40100 · Invariants : I8, I10

## Objectif
Affiner les source-maps de la **ligne** à l'**expression** (différé V6/60200, V9/5.3). Prérequis de la
remontée précise de l'overlay rustc (60800) et du LSP : pour pointer la bonne sous-expression Iron quand
rustc se plaint d'un appel/opérateur particulier.

## Périmètre
- Émettre un **marqueur invisible** (`__irn_mark!(idx)`, no-op, I10) par **expression significative** (appels,
  opérateurs, accès champ/index, méthodes externes, `await`, `?`), pas seulement par stmt.
- `SpanLink` par expression ; la résolution (60800/driver) choisit le lien le **plus fin** couvrant la position
  Rust.
- Borner aux expressions « intéressantes » (pas les littéraux) pour le volume.

## Hors-périmètre
- Debug-info DWARF (on reste sur la remontée textuelle rustc, sauf 72300).

## Comportement attendu
Erreur rustc sur `r.is_match(x)` dans une ligne composite → remontée pointe **`r.is_match(x)`**, pas la ligne.

## Contrat / interface
`sourcemap` + `lower` : `SpanLink` par expression ; `driver::remontee` résout au lien le plus fin.

## Source maps (I8)
**C'est la spec.** Toute spec de codegen V9.1 (génériques, async, idiomes) en bénéficie. Le debugger (72300)
et le LSP (71300) consomment cette granularité.

## Critères d'acceptation
- Erreur dans une sous-expression → remontée pointe l'**expression** (test de précision).
- Marqueurs = no-op (corpus vert, sémantique inchangée).
- L'overlay rustc (60800) gagne en précision (mesuré sur cas types).

## Décomposition
→ planif `B2` : marqueurs par expression, résolution fine, tests de précision.

## Risques / questions ouvertes
- 🔶 Volume de marqueurs (un par expression) → coût compilation/lisibilité du Rust généré ; borner.
