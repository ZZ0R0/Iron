# [21000] Closures de 1ʳᵉ classe / fonctions d'ordre supérieur

- Version : V18
- Milestone : self-suffisance
- Statut : draft
- Dépend de : [20700] (closures inline existantes), [21700+] (moteur d'inférence I15), [70400] (garde)
- Invariants applicables : I1, I6, I15

## Objectif
Rendre les **closures** réellement de 1ʳᵉ classe : passables en argument à des **fonctions utilisateur** (pas
seulement aux bindings externes via l'idiome `closure`), **retournées**, **stockées** ; avec un lowering qui
choisit `impl Fn`/générique borné ou `Box<dyn Fn>` selon le besoin. C'est **le** gap de langage qui élargit le
plus le périmètre : callbacks, combinateurs, `map`/`filter`/`fold` riches, et les crates **closure/trait-lourds**
(nom 16 %, itertools 32 %) que la frontière du binder bloque aujourd'hui.

## Périmètre
- **Higher-order fns utilisateur** : `def apply(f, x): return f(x)` ; `def compose(f, g): return lambda x: f(g(x))`.
- **Closures en argument** d'une fn utilisateur (param de type fonction inféré `fn(A)->B`).
- **Closures retournées** (le type reste **explicite** — l'exception I15 assumée).
- **Closures stockées** (champ de struct de type fonction → `Box<dyn Fn>` probable).
- **Lowering** : monomorphisation (`impl Fn`) par défaut ; `Box<dyn Fn>` quand stocké/hétérogène.

## Hors-périmètre
- Générateurs/coroutines complexes (lazy/infini, `yield from`) → `rust{}` (bloc « 0.1% »).
- Closures capturant un état mutable partagé non trivial → `shared` explicite (I3).

## Comportement attendu
```python
def apply(f, x):              # f inféré `fn(T)->U` depuis le site d'appel
    return f(x)
def main():
    print(apply(lambda n: n * 2, 21))     # 42
    fns = [lambda x: x+1, lambda x: x*x]   # list de closures (Box<dyn Fn> homogène)
    print(fns[1](5))                       # 25
```
```python
def adder(n):                 # closure RETOURNÉE → type explicite requis (I15)
    return lambda x: x + n    # capture n par valeur
```
- **Iron → Rust** : `apply` → `fn apply<F: Fn(T)->U>(f: F, x: T) -> U`. Closure arg → la lambda Rust.
  Closure stockée/retournée → `Box<dyn Fn(T)->U>` (capture `move` des variables possédées).

## Contrat / interface
- L'inférence **propage** le type fonction d'un site d'appel vers le param (`fn(A)->B`), via le moteur I15.
- **Décision figée** : par défaut **monomorphisation** (`impl Fn`, coût nul) ; **trait-objet** (`Box<dyn Fn>`)
  seulement quand l'usage l'exige (stockage en collection/champ, retour hétérogène). La capture est `move`
  sur les variables **possédées** (sémantique valeur), emprunt sinon.
- `rustc` filet (I2) pour les cas de durée de vie de capture non couverts.

## Source maps
Le lowering des closures (lambda/Closure → closure Rust) préserve les spans (I8) comme tout lowering.

## Critères d'acceptation (validés par [70400])
- `apply(lambda n: n*2, 21)` → **42** (run réel).
- Une closure **stockée** dans une liste/un champ et rappelée fonctionne.
- Une closure **retournée** (avec type explicite) fonctionne (`adder(10)(5)` → 15).
- Un mini-programme à **combinateurs** (ou un crate closure-lourd via curation) progresse mesurablement.
- Corpus [70400] vert.

## Décomposition
→ Planif V18 (après [70400]) : inférence du type fonction (moteur), lowering `impl Fn`/`Box<dyn Fn>`, capture.

## Risques / questions ouvertes
- **🔴 Durées de vie de capture** : une closure qui capture un emprunt et survit → problème de lifetime
  (le 0.1%). Conservateur : capture `move` (possède) quand faisable ; sinon diagnostic / `rust{}`.
- **❓ Monomorphisation vs Box** : critère de bascule (stockage/retour hétérogène) à préciser en planif.
