# [21300] Async / concurrence — un modèle usable, borné

- Version : V18
- Milestone : self-suffisance
- Statut : draft
- Dépend de : [21200] (async def existant, tokio injecté), [30700] (shared_sync existant), [70400] (garde)
- Invariants applicables : I1, I2, I5, bloc « 0.1% »

## Objectif
Donner à Iron un modèle **async/concurrent usable** (serveurs, outils concurrents, parallélisme de calcul)
dans ses contraintes (sémantique valeur, zéro `unsafe`, runtime opt-in). Aujourd'hui : `async def` existe (→
`async fn` + tokio injecté) et `thread.spawn` existe, mais l'**ergonomie** est pénible (cf. `RAPPORT_IRON`
§2.6 : closures `move` capturant des `Copy` seulement, reconstruire scène/caméra par worker). On vise un
modèle **propre et borné** — pas l'async exotique (qui reste `rust{}`).

## Périmètre
- **(a) async/await** : `async def` + `await e` (existant) consolidés ; un programme async simple (requêtes
  concurrentes) tourne. Runtime **opt-in** (tokio injecté **seulement si** `async` est utilisé — I5 préservé).
- **(b) Parallélisme de calcul à données partagées en lecture** : `thread.scope` — capturer `&data`
  (la scène du raytracer !) **sans clone ni reconstruction**. Résout §2.6 du rapport (la chorégraphie pénible).
- **(c) Primitives de partage** : `shared_sync[T]` (= `Arc<Mutex<T>>`, existant) consolidé pour l'état mutable
  partagé entre threads ; canaux (`channel`) **à évaluer** (mpsc) pour le passage de messages.

## Hors-périmètre (reste `rust{}` — bloc « 0.1% »)
- Async **exotique** : `select!`, pinning, streams, async-traits, runtimes custom.
- Ordonnancement fin / lock-free / unsafe concurrency.

## Comportement attendu
```python
# (b) parallélisme à scène partagée en LECTURE (le cas raytracer, proprement) :
def render(scene, w, h):
    thread.scope(lambda s:                 # capture &scene sans clone
        for band in bands:
            s.spawn(lambda: render_band(scene, band)))   # &scene partagé
```
```python
# (a) async simple :
async def fetch_all(urls):
    results = []
    for u in urls:
        results.append(await get(u))
    return results
```
- **Iron → Rust** : `thread.scope(…)` → `std::thread::scope(|s| …)` ; `&scene` capturé partagé (pas de `move`
  d'une struct possédée). `async def` → `async fn` + `#[tokio::main]` sur `main` (si async présent).

## Contrat / interface
- **Décision figée (périmètre)** : Iron commit à **async/await basique + thread.scope + shared_sync**. Tout
  le reste = `rust{}`. Pas de promesse d'async général.
- **Runtime opt-in** (I5) : tokio injecté **uniquement** si un `async def` existe ; sinon zéro runtime.
- **Partage en lecture** : `thread.scope` permet de capturer `&data` (s'appuie sur l'ownership V17 : la donnée
  est empruntée, pas clonée). C'est le **bénéfice direct** du socle ownership.
- `rustc` filet (I2) ; jamais d'`unsafe` émis par Iron.

## Critères d'acceptation (validés par [70400])
- **(a)** un programme `async` simple (ex. addition concurrente / faux-fetch) compile + run.
- **(b)** **le raytracer parallélise via `thread.scope(&scene)`** — **sans** reconstruire scène/caméra par
  worker (la chorégraphie §2.6 disparaît) ; image correcte ; perf ≥ la version threads actuelle.
- Corpus [70400] vert ; 0 `unsafe`.

## Décomposition
→ Planif V18 (sous [70400]) : (b) thread.scope d'abord (bénéfice ownership immédiat, le plus utile pour le
calcul) ; (a) async consolidé ; (c) canaux si le besoin émerge.

## Risques / questions ouvertes
- **🔴 Le plus gros lift de V18.** Le scoping borné (commit à un sous-ensemble) est la clé pour ne pas
  exploser. Si un cas dépasse → `rust{}`, assumé.
- **❓ Canaux (mpsc)** : utile mais ajoute de la surface ; à inclure seulement si un cas du corpus le demande.
- **❓ `thread.scope` + closures** : dépend de [21000] (closures de 1ʳᵉ classe) pour les lambdas de worker —
  **synergie** : faire [21000] avant ou avec (b).
